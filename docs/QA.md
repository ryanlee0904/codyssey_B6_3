# 예상 질문과 답변 (발표·코드 리뷰용)

답변은 이 프로젝트 코드 기준이며, 괄호 안은 근거가 되는 파일입니다.

---

## A. 인증 / 인가 (Depends)

**Q1. 로그인 상태를 어떻게 유지하나요?**
로그인 성공 시 세션에 `user_id` 하나만 저장합니다. `SessionMiddleware` 가 이를 `itsdangerous` 로 서명한 쿠키로 내려주고, 다음 요청에서 쿠키를 검증해 `request.session` 으로 복원합니다. (`auth/session.py`, `main.py`)

**Q2. 쿠키에 user_id 가 들어 있으면, 사용자가 숫자를 바꿔서 다른 사람으로 로그인할 수 있지 않나요?**
불가능합니다. 쿠키는 서버의 `SECRET_KEY` 로 서명되어 있어 내용을 바꾸면 서명 검증에 실패하고 세션이 비어 있는 것으로 처리됩니다. 그래서 운영 환경에서는 `SECRET_KEY` 를 반드시 환경 변수로 바꿔야 합니다. (`core/config.py`)

**Q3. `get_current_user_optional` 과 `login_required` 를 왜 나눴나요?**
공개 페이지(홈, 로그인)는 로그인 여부를 **알아야** 하지만(UI 분기) **막으면 안** 됩니다. 보호 페이지는 막아야 합니다. 그래서 "조회"(optional)와 "강제"(required)를 분리하고, `login_required` 가 `optional` 을 의존하도록 체인으로 연결했습니다. (`auth/dependencies.py`)

**Q4. 라우터에 `dependencies=[Depends(login_required)]` 를 걸었는데 핸들러에도 `Depends(login_required)` 가 있습니다. 두 번 실행되나요?**
아닙니다. FastAPI 는 한 요청 안에서 같은 의존성 결과를 캐시합니다. 라우터 쪽은 "이 라우터 전체를 보호한다"는 안전장치, 핸들러 쪽은 "User 객체를 받아 쓰기 위한" 선언입니다.

**Q5. 왜 JWT 가 아니라 세션을 선택했나요?**
① Jinja2 SSR 이라 브라우저가 쿠키를 자동 전송해 추가 코드가 필요 없고, ② 로그아웃 시 세션을 비우면 즉시 무효화되며(JWT 는 만료 전까지 유효), ③ flash 메시지·next 경로 같은 화면 흐름 상태도 세션에 함께 담을 수 있기 때문입니다.

**Q6. 비밀번호는 어떻게 저장하나요? passlib 은 왜 안 썼나요?**
`bcrypt` 로 해시(솔트 포함)해서 저장하고 평문은 저장하지 않습니다. passlib 1.7.4 는 관리가 중단되었고 bcrypt 4.1+ 와 함께 쓰면 버전 탐지 오류가 나서, 허용 패키지 범위 안의 bcrypt 를 직접 사용했습니다. (`auth/security.py`)

**Q7. 로그인 실패 시 "아이디가 없다"와 "비밀번호가 틀렸다"를 구분하지 않는 이유는?**
구분해서 알려주면 어떤 아이디가 가입되어 있는지 외부에서 알아낼 수 있습니다(계정 열거). 그래서 "아이디 또는 비밀번호가 올바르지 않습니다"로 통일했습니다. (`services/auth_service.py`)

**Q8. 로그인할 때 `session.clear()` 를 먼저 하는 이유는?**
로그인 전 세션을 그대로 이어 쓰면 세션 고정(session fixation) 공격에 취약합니다. 로그인 시점에 세션을 새로 시작합니다.

## B. 접근 제어 (비로그인 차단)

**Q9. 비로그인 사용자가 `/app/orders` 에 접근하면 정확히 어떤 일이 일어나나요?**
① 라우터 의존성 `login_required` 가 사용자 없음을 확인하고 `LoginRequiredException(next_url="/app/orders")` 를 던짐 → ② 핸들러는 실행되지 않음 → ③ `main.py` 의 예외 핸들러가 "로그인이 필요한 페이지입니다" flash 를 남기고 `303 /login?next=/app/orders` 로 리다이렉트 → ④ 로그인 성공 후 `/app/orders` 로 복귀.

**Q10. 왜 의존성에서 바로 `RedirectResponse` 를 반환하지 않고 예외를 던지나요?**
의존성의 반환값은 핸들러의 인자로 들어가므로 응답을 대신할 수 없습니다. 예외를 던지면 핸들러 실행을 중단할 수 있고, 응답 형태(리다이렉트, 안내 메시지)는 `main.py` 한곳에서 정할 수 있습니다.

**Q11. `next` 파라미터를 그대로 쓰면 위험하지 않나요?**
`/login?next=https://악성사이트` 처럼 외부로 보내는 open redirect 가 생길 수 있습니다. `safe_redirect_path()` 가 `/` 로 시작하고 `//` 로 시작하지 않는 내부 경로만 허용합니다. (`auth/session.py`)

**Q12. 로그인한 사용자가 남의 주문 번호를 URL 에 입력하면?**
인증은 통과하지만, 서비스 계층이 "구매자 본인 또는 해당 상품의 판매자인가"를 확인해 `PermissionDeniedError` → 403 화면을 보여줍니다. 인증(로그인 여부)과 소유권 확인을 분리했습니다. (`services/order_service.get_order_for_view`)

**Q13. 로그아웃이 왜 GET 이 아니라 POST 인가요?**
GET 은 링크나 이미지 태그만으로도 호출될 수 있어, 다른 페이지가 사용자를 몰래 로그아웃시킬 수 있습니다. 상태를 바꾸는 요청은 POST 로 처리했습니다.

## C. SQLAlchemy 연관관계

**Q14. 모델 간 관계를 설명해 주세요.**
User 1:N Order(구매자), User 1:N Goods(판매자), Goods 1:N Order 세 가지이며 모두 `back_populates` 로 양방향입니다. 결과적으로 User 와 Goods 의 N:M 관계를 Order 라는 중간 모델로 풀었습니다.

**Q15. 그냥 user_goods 연결 테이블로 N:M 을 만들면 안 되나요?**
주문에는 수량, 주문 시점 단가, 상태, 배송/취소 시각 같은 고유 데이터가 있습니다. 연결 테이블은 두 키만 담는 용도라 이런 속성과 상태 변경 로직을 담을 수 없어서 독립 모델로 만들었습니다.

**Q16. `back_populates` 가 없으면 어떻게 되나요?**
한쪽에서 관계를 설정해도 반대쪽 컬렉션이 메모리에서 갱신되지 않아, 커밋 전에는 `user.orders` 에 새 주문이 보이지 않는 등 객체 상태가 어긋납니다. 양쪽을 명시적으로 연결해 일관성을 유지합니다.

**Q17. 왜 `unit_price` 를 따로 저장하나요? `goods.price` 를 쓰면 되지 않나요?**
상품 가격은 나중에 바뀔 수 있습니다. 과거 주문의 결제 금액은 바뀌면 안 되므로 주문 시점 가격을 스냅샷으로 저장합니다.

**Q18. 회원을 삭제하면 주문은 어떻게 되나요? 상품은요?**
- 주문: `cascade="all, delete-orphan"` → 함께 삭제. 구매자 개인 데이터라 탈퇴 시 파기하는 것이 맞다고 판단했습니다.
- 상품: FK `RESTRICT` → 상품이 남아 있으면 회원 삭제 불가. 상품에는 다른 회원의 주문이 달려 있어 함께 지우면 남의 거래 기록이 깨집니다.
(`models/user.py` 주석)

**Q19. 주문이 있는 상품을 삭제하려 하면?**
서비스가 먼저 `has_orders()` 로 확인해 "주문 이력이 있는 상품은 삭제할 수 없습니다"라고 안내합니다. 서비스 검사를 우회하더라도 DB 의 `RESTRICT` 제약이 최종 안전장치 역할을 합니다. (`services/goods_service.delete_goods`)

**Q20. `passive_deletes="all"` 은 무슨 역할인가요?**
부모를 삭제할 때 SQLAlchemy 가 자식 행의 FK 를 임의로 NULL 로 바꾸지 않고, DB 의 FK 제약(RESTRICT)에 판단을 맡기게 합니다.

**Q21. SQLite 에서 FK 제약이 정말 동작하나요?**
SQLite 는 기본으로 FK 검사를 하지 않습니다. 커넥션마다 `PRAGMA foreign_keys=ON` 을 실행하도록 이벤트 리스너를 등록했습니다. (`core/database.py`)

**Q22. N+1 쿼리 문제는 어떻게 처리했나요?**
리포지토리에서 `joinedload`(N:1, 한 건)와 `selectinload`(1:N, 컬렉션)로 화면에 필요한 관계를 미리 로딩합니다. 예를 들어 주문 목록은 주문 + 상품 + 판매자를 한 번에 가져와 템플릿이 `o.goods.seller.nickname` 을 출력해도 추가 쿼리가 없습니다. (`repositories/*.py`)

## D. 상태 변경 로직

**Q23. 이 서비스의 "상태 변경 기능"은 무엇인가요?**
주문 상태 전이입니다. 주문접수 → 배송중(판매자) → 배송완료(구매자), 주문접수 → 주문취소(구매자, 재고 복구).

**Q24. `status` 를 그냥 UPDATE 하면 안 되나요?**
그러면 배송완료를 다시 주문접수로 돌리거나, 취소했는데 재고가 복구되지 않거나, 구매자가 배송 시작을 누르는 일이 가능해집니다. 상태 변경은 규칙·권한·부수효과가 함께 움직이는 비즈니스 행위라서 전용 로직으로 처리했습니다.

**Q25. 허용되는 전이 규칙은 어디에 정의되어 있나요?**
`models/order.py` 의 `ALLOWED_TRANSITIONS` 표입니다. 규칙을 데이터(표)로 두어 한눈에 보이고, 규칙을 바꿀 때 이 표만 수정하면 됩니다.

**Q26. 그 규칙은 어디서 강제되나요?**
`services/order_service.py` 의 `_transition()` 이 현재 상태에서 목표 상태로 갈 수 있는지 검사하고, 안 되면 `BusinessError` 를 던집니다. 각 행위(`cancel_order`, `ship_order`, `confirm_delivery`)는 먼저 권한을 확인한 뒤 `_transition()` 을 호출합니다.

**Q27. 화면에서 버튼을 숨기면 충분하지 않나요?**
아닙니다. 버튼을 숨겨도 개발자 도구나 직접 POST 요청으로 호출할 수 있습니다. 템플릿은 "보여주기"만 하고, 최종 판단은 항상 서버의 서비스 계층이 합니다.

**Q28. 상태 변경 전/후는 어떻게 보여주나요?**
`_transition()` 이 `StatusChange(order, before, after)` 를 반환하고, 라우터가 "주문 #3 상태 변경: 주문접수 → 주문취소" 메시지로 보여줍니다. 상세 화면에는 진행바와 시각이 기록된 상태 이력이 표시됩니다.

**Q29. 취소할 때 상태는 바뀌었는데 재고 복구가 실패하면?**
상태 변경, 취소 시각 기록, 재고 복구가 같은 트랜잭션에서 `commit` 한 번으로 처리되므로, 중간에 실패하면 모두 반영되지 않습니다.

**Q30. 주문할 때 재고는 어떻게 처리하나요?**
`place_order()` 가 본인 상품 주문 금지, 수량 범위, 재고 부족을 검사한 뒤 재고를 차감하고 주문을 만들어 같은 트랜잭션으로 커밋합니다. (동시에 많은 요청이 들어오는 상황의 잠금 처리는 이번 범위에서 다루지 않았습니다.)

## E. 전체 구조와 계층 분리

**Q31. 계층을 왜 이렇게 나눴나요?**
각 계층이 하나의 이유로만 바뀌게 하기 위해서입니다. 라우터는 HTTP(폼, 리다이렉트), 서비스는 비즈니스 규칙과 트랜잭션, 리포지토리는 쿼리, 모델은 테이블과 관계, 템플릿은 표시만 담당합니다. 규칙을 바꾸면 서비스만, 화면을 바꾸면 템플릿만 고칩니다.

**Q32. 서비스 계층이 HTTP 를 모른다는 게 무슨 뜻인가요?**
서비스는 `Request`, 상태 코드, 리다이렉트를 사용하지 않고 `BusinessError` / `NotFoundError` / `PermissionDeniedError` 같은 도메인 예외만 던집니다. 이를 flash 메시지, 404, 403 화면으로 바꾸는 것은 라우터와 `main.py` 의 일입니다. 덕분에 같은 서비스를 나중에 JSON API 에서도 재사용할 수 있습니다.

**Q33. commit 은 왜 리포지토리가 아니라 서비스에서 하나요?**
하나의 비즈니스 행위(예: 취소 = 상태 변경 + 재고 복구)가 여러 리포지토리 작업을 묶어야 하기 때문입니다. 트랜잭션의 경계는 "업무 단위"를 아는 서비스가 정합니다.

**Q34. 폼 제출 후 왜 항상 303 리다이렉트를 하나요?**
POST 결과 화면을 바로 렌더링하면 새로고침 시 같은 주문이 다시 전송될 수 있습니다. POST → 303 → GET (PRG 패턴)으로 중복 제출을 막았습니다.

**Q35. 사용자 관점에서 전체 흐름을 설명해 주세요.**
홈에서 로그인 → 상품 목록·상세 → 주문하면 주문접수 상태로 생성 → 구매자는 취소 또는 수령 확인, 판매자는 판매 관리에서 배송 시작 → 각 변경 결과를 메시지·진행바·마이페이지에서 확인.

**Q36. 개발자 관점에서 요청 하나의 흐름을 설명해 주세요.**
`POST /app/orders/3/cancel` 기준: SessionMiddleware 가 쿠키를 세션으로 복원 → 라우터 의존성 `get_db → get_current_user_optional → login_required` → `routers/orders.py` 가 서비스 호출 → `order_service.cancel_order()` 가 권한·전이 검증, 재고 복구, commit → 303 → `GET /app/orders/3` 에서 리포지토리가 관계를 로딩하고 Jinja2 가 결과를 렌더링.

**Q37. 더 발전시킨다면 무엇을 하겠나요?**
- 재고 차감 시 동시성 제어(행 잠금 또는 조건부 UPDATE)
- CSRF 토큰 추가 (현재는 SameSite=Lax 쿠키로 기본 방어)
- 운영 환경에서 HTTPS + `https_only=True`, `SECRET_KEY` 환경 변수화
- Alembic 마이그레이션, 테스트 코드(pytest) 추가
- 주문 1건에 여러 상품을 담는 OrderItem 모델 분리
